# 排查记录：界面截屏「控件树不可用」+ 结果表里冒出莫名警告

- **日期**：2026-11-11
- **版本**：v2.0.4
- **涉及文件**：`backend/sender.py`、`backend/myhistory.py`、`frontend/index.html`

## 用户报告的现象（截图）

1. 结果表格顶部出现一条**被截断的黄色警告**：「在 4.1.15.13 / 4.1.15.53 上
   完整验证过。微信升级会改变 accessibility gate 的位置……建议关闭微信自动更新
   并退回已验证版本。」
2. 每个群都显示「界面：微信控件树不可用，无法走界面截屏；可改用「本地库导出」」
3. 本地库导出正常（群 `220212`，697 条本人消息）
4. 「自动识别完成 · 共 175 个群」

## 逐条定性

| 现象 | 结论 |
|---|---|
| 顶部截断警告 | **渲染 bug**，不是新警告。后端把引擎初始化异常塞成一条 `group="(引擎)"` 的伪结果，前端 `myRenderResults` 当普通群渲染，长文本里的换行 hint 被表格行截断，看起来像凭空冒出一段没头没尾的话 |
| 控件树不可用 | **真故障，但不是版本不支持**（详见下节） |
| 群名 `220212` | **不是 bug**。导出 JSON 里 `group="220212"`、`username=57692391736@chatroom`，是真实群备注 |
| 175 个群 | **不是 bug**。日志 `账号=wxid_be7yiiqekf5q22_fe8f 群=175 好友=399`，当前账号真实数量 |

## 根因：前置步骤没做对 + 第三方误报 + 无效重试

### 证据链

| 证据 | 值 |
|---|---|
| 微信版本 | **4.2.0.13**（`C:\soft\Weixin\`，目录里还有 4.2.0.11） |
| `electron.log` 15:50:26–15:50:51 | 4 条「UIA 树已物化，已记录 gate RVA：`Weixin.dll+0xb50abc8`」，间隔约 8 秒 |
| 8 秒间隔的来源 | `_uia_ready(timeout=4.0)` 跑满 + `sleep(1.0)` + `_ensure_uia` 的 `sleep(2.5)`，即**每次验收都失败、白等 4 轮** |
| 16:02 只读诊断 | 微信窗口 `vis=0`（托盘隐藏），根 `mmui::MainWindow` 但 6 层内 **0 个 mmui 子控件**、`MainView` 不存在 = 空壳 |
| 16:22 诊断（`ShowWindow`+`SetForegroundWindow`+唤醒 gate 后） | **61 个 mmui 控件**，`_uia_ready=True` |
| 16:25 受控实验（再隐藏） | 仍 40 个 mmui、`_uia_ready=True` —— 物化是一次性、不可逆状态，隐藏不会让它退化 |
| 第三方 `wechatauto.accessibility._mmui_present()` | 只要**根控件 ClassName 以 `mmui::` 开头**就返回 True 并打日志「UIA 树已物化」，**空壳也算成功** |

### 结论

**这不是「微信 4.2.0.13 不支持」**。4.2.0.13 上实测能物化出 61 个 mmui 控件、
`_uia_ready` 返回 True。真正的问题是：

1. 微信藏在托盘时 Qt 不构建 mmui 子控件树，gate 字节再怎么写也是空壳。
2. `ensure_window_visible()` 只在 `_ensure_uia()` **开头调一次**；`SetForegroundWindow`
   受 Windows 前台锁定限制会失败，异常被 `except: pass` 吞掉，后面 3 轮重试
   **再没重试「把窗口叫出来」**。
3. 第三方 `wake(verify=True)` 用自己的宽松口径误报成功，日志变成「4 次都成功」
   的假象，掩盖了真实原因。
4. 失败文案武断地建议「退回 4.1.15.x 已验证版本」——与实测矛盾，且不可操作。

### 两个被纠正的错误假设（诚实记录）

排查过程中先后有两个假设被证据推翻，都写在这里避免以后重踩：

- **假设 A：「我们的验收过严，是误判，应放宽到与第三方对齐」** —— 错。
  `docs/排查记录-微信4.2.0.11控件树失效.md` 早已写明「库的『已验证』是它自己的
  判定口径，与控件树是否真的出现并不等价」。我们的严格验收正是 v2.0.2
  「47 张全群消息」误截事故的防线，放宽等于把事故放回来。
- **假设 B：「窗口可见性是根因，隐藏就会退化成空壳」** —— 错。
  受控实验隐藏已物化的窗口后仍有 40 个 mmui、验收仍通过。可见性只影响
  **首次物化**，不影响已物化的树。

## 修复（用户拍板：保留严格验收 + 快速失败 + 准确提示 + 想办法搞定）

| 处 | 改动 |
|---|---|
| `sender.ensure_window_visible()` | 改为返回 `bool`；`SW_RESTORE`+`SW_SHOW`+`SW_SHOWNORMAL` 三重保险；`SetForegroundWindow` 失败时用 `AttachThreadInput` 附加前台线程输入队列兜底 + `BringWindowToTop`；最后**验证** `IsWindowVisible`，不再静默吞异常 |
| `sender.wake_accessibility()` | **每轮**重试都先重新确保窗口可见；注释明确第三方 `wake(verify=True)` 的空壳误报口径，一律以本项目 `_uia_ready` 为准；去掉失败后才补一次可见性的旧逻辑 |
| `sender._uia_ready()` | **完全不动**，保留 `MainView` / ≥3 个 mmui 子控件的严格验收 |
| `VERIFIED_WECHAT_VERSIONS` | 加入 4.2.0.13（实测可用）；明确「版本只用于诊断信息，不参与放行判断」 |
| `sender._ensure_uia()` 失败文案 | 改为准确且可操作：说明「gate 已写入但树仍是空壳」，给出三步（点开微信保持前台 / 退出重登后点「探测控件树」/ 重启本程序），并说明本地库导出不受影响；**删掉「退回已验证版本」** |
| `myhistory._Job` | 新增 `engine_error` 字段，`snapshot()` 暴露，`start()` 每轮清空；引擎失败写独立字段，**不再塞 `group="(引擎)"` 伪结果行**；`JOB.log` 提示本地库继续 |
| `frontend/index.html` | 新增 `myEngineWarn` 独立提示条（完整 `white-space:pre-wrap` 不截断、可关闭、出现/消失过渡动画、按钮轻微缩放）；`myPoll` 读 `engine_error`；`myRenderResults` 过滤 `(引擎)` 伪行；`myStart` 开新一轮时重置；`myHelp` 说明界面模式需微信在前台 |

`server.py` 的 `/api/myhistory/status` 用 `**status()` 展开，自动带上 `engine_error`，无需改动。

## 验证

| 项 | 结果 |
|---|---|
| 综合静态 + 语法测试 | 42/42 |
| **真实 UIA 判定**（当前窗口） | `VIS True` / `READY True` / `WAKE True` |
| **端到端自愈**：先隐藏窗口，只调 `wake_accessibility(retries=2)`，不手工 ShowWindow | **4/4**：自动叫回前台（`vis=1`）、树验收通过、返回 True、窗口恢复原状 |

自愈测试正是复现用户 15:50 的失败前置状态，修复后不再失败。

## 已知限制

1. **未做真机「界面八步截屏」端到端**：那需要用户在场点「开始查找」并观察微信
   窗口被操作，会改动使用者桌面状态。已验证的是引擎初始化与控件树物化链路。
2. 若微信冷启动后 gate 字节被重置且窗口长期藏在托盘，首次仍需由
   `wake_accessibility` 把窗口叫出来；这一步现在每轮重试都会做。
3. 顶部提示条只在「引擎初始化失败」时出现。单个群自己的 UI 失败（如找不到
   「群成员」按钮）仍走结果表格里原有的 `界面：...` 行，两者不混淆。
