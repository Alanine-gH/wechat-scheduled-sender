# 设计文档 · 我的群消息（本人在群里发了什么）

> 版本：v2.0.1
> 日期：2026-11-10
> 涉及文件：`backend/myhistory.py`（新增）、`backend/settings.py`、`backend/server.py`、`frontend/index.html`

## 需求

给一条能用的路径，把「本人在某个群里发过什么」找出来，并截屏留证。
用户给的微信手工流程：

1. 打开群，点右上角三个点
2. 下拉找「查找聊天内容」
3. 点开「查找聊天记录」窗口
4. 点「群成员」
5. 搜索本人在群中的昵称 / 本人昵称
6. 下拉找到本人头像
7. 点头像
8. 截屏

**追加硬约束（用户）**：「为什么要用户填写？做到自动读取！如果选中了多个群的
群昵称不一样就直接自动化，减少用户操作难度。」

## 前提核实（动手前先查，避免逻辑跳跃）

| 前提 | 核实结果 |
|---|---|
| 项目本来能否直接读聊天库 | 能。`wechatauto.WeChatDB.get_messages()` 带 `sender_username`，可直接按本人 wxid 过滤，全量导出，不碰界面 |
| 「查找聊天记录」是不是独立窗口 | 是。只读枚举确认主窗口是 `Qt51514QWindowIcon`，聊天记录窗口标题形如 `"群名"的聊天记录(426)` |
| 新窗口控件名能否凭空确定 | 不能。微信最小化 / gate 未激活时 UIA 树只剩 1 个 `MainWindow` 根节点 |
| 群昵称存在哪里 | **`contact.db` → `chat_room.ext_buffer`**，protobuf `repeated ChatRoomMember`：`field1=成员wxid`、`field2=群昵称`、`field3=flag`、`field4=邀请人` |
| 本机真值 | `self_info.nick_name='1'`，`wxid_gz8zi2hnu93y22`；29 个群里 28 个没设群昵称（退回微信昵称 `1`），1 个设了 `sj_small` |

`chatroom_member` 表只有 `room_id/member_id`，**没有群昵称列**——这是最容易踩的坑：
只看表结构会得出「群昵称读不到、只能让用户填」的错误结论，实际昵称在
`ext_buffer` 的 protobuf 里。

## 方案：两条路 + 昵称全自动

| 路 | 做法 | 需要用户填东西吗 |
|---|---|---|
| `ui` 界面截屏 | 按 8 步用 UIA 控件树操作，逐屏 `PrintWindow` 截图 | 不需要 |
| `db` 本地库导出 | `get_messages()` 按 `sender_username == 本人wxid` 过滤，导出 JSON/TXT | 不需要 |
| `both` | 两者都跑 | 不需要 |

### 昵称自动识别（核心）

`group_display_names(db)` 返回 `{群username: [候选名...]}`：

1. 打开 `contact.db`（用 `WeChatDB._contact_conn()` 拿**已解密**连接；
   直接 `sqlite3.connect` 会报 `file is not a database`）
2. 读本人 `contact` 行的 `nick_name / remark / alias`，加 `get_self_info()`，
   再加 `wxid` 作为全局候选
3. 逐群解析 `chat_room.ext_buffer`：手写最小 protobuf 解码
   （`_pb_fields` 只认 varint / length-delimited / 32 / 64 位，**不引入第三方库**），
   找到 `field1 == 本人wxid` 的那条记录，取 `field2` 作为**该群的群昵称**
4. 群昵称排最前，后面依次补全局候选；没设群昵称的群自然退回微信昵称
5. `_worker` 里 `nicks = per_group.get(username) + fallback`，
   **每个群用自己的名字**，选中多个群且昵称各不相同也能各自对上

前端因此**删掉了必填输入框**，只保留一个「补充昵称（可留空）」作为兜底；
启动时 `/api/myhistory/self` 返回识别结果，界面显示
「自动识别完成 · 共 29 个群 · 微信昵称：1 · 其中 1 个群设置了不同的群昵称 sj_small · 全程无需填写」。

## UIA 实现要点（严守「不用坐标」红线）

- **按进程 PID 归属枚举窗口**（`_wechat_pids` + `GetWindowThreadProcessId`）：
  微信浮层类名可能是 `QWindowIcon` / `QWindowTool` / 换 Qt 版本后的新类名，
  认类名会漏；按 PID 认最稳。本机实测识别到 5 个微信进程、18 个相关窗口
  （按旧类名规则只能找到 2 个）。
- `_roots()` 过滤掉隐藏 / 零尺寸窗口，避免逐个 `ControlFromHandle` 卡死。
- **跨窗口找控件**（`find_anywhere`）：「搜索群成员」结果是独立 Qt 浮层，
  只在聊天记录窗口的树里找必然漏。
- **下拉重试**（`find_scrolling`）：用户步骤 2、6 明确要下拉，
  Qt 虚拟列表不会把屏幕外的项放进 UIA 树；用键盘 `PageDown` 逐批找，
  不碰滚轮坐标。
- **搜索用真实输入事件**（`set_text(prefer_keys=True)`）：
  微信搜索框靠输入事件触发筛选，`ValuePattern.SetValue` 有时只改值不刷新结果。
- **候选名可配置**：`MORE_NAMES / FIND_NAMES / MEMBER_TAB_NAMES / SEARCH_NAMES`
  + 设置项 `myhistory_names_extra`，微信改版不用改代码；
  `探测控件树` 按钮把真实控件树写到 `logs/uia_trees_*.json` 供校准。
- 所有点击走 `Click()` / `InvokePattern`，输入走 `ValuePattern` / `SendKeys`，
  **零坐标、零剪贴板**。
- 界面模式遵守 `shot_enabled` 开关（关了就拒绝启动，提示改用本地库导出）。

## 已知限制（诚实说明）

1. **UI 八步未经真机端到端验证**：本机微信当时最小化 / gate 未激活，
   控件树只有 1 个根节点，无法在不打扰用户微信的前提下跑完整流程。
   所以做了「候选名可配置 + 探测控件树 + 每步明确报错」三道兜底。
   用户点一次「开始查找」即可实测；若某步找不到，`logs/myhistory_tree_*.json`
   会记录真实控件名，填到设置里就能适配，不必改代码。
2. **`db` 路依赖本地库解密可用**，且只覆盖已落库的近期消息（`cap=3000`）。
   它是主推路线：零输入、全量、不碰微信窗口。
3. `ext_buffer` 的 protobuf 字段含义是本机 4.x 实测反推的；
   微信换版本若改字段，`group_display_names` 会返回空表并自动退回全局昵称，
   不会让功能挂死。
4. 群昵称识别按 `chat_room` 的 `username` 索引；目标必须带 `username`（前端
   `state.selected` 里本来就有）。
