# 设计文档：运营方案自动化（v1.2.0）

- **日期**：2026-11-03
- **来源**：`粮食反向开票业务·财税广告群营销方案（最终版）.docx`
- **目标**：把这套人工运营流程里能自动化的部分做成工具能力

## 一、方案要点 → 工具能力的映射

| 方案要求 | 原工具 | 本次新增 |
|---|---|---|
| 每天 1 条，固定晚 8 点发 | 只有「两条之间随机等 N 分钟」 | `scheduler.py` 绝对时间事件表 |
| 引导语按周一~周日轮换 | 消息池随机抽 | `campaign.py` 按星期取引导语 |
| 引导语 + 原文案（原文案一字不改） | 只能发整条 | `campaign.compose()` |
| 文案发出 30 分钟后补发钩子 | 一条发完即结束 | 事件表里的 hook 事件 |
| 钩子每周 2-3 次（周二/四/六） | 无频次概念 | `hook_days` + 每群每周上限 |
| **群友主动私聊人数** 等 4 项 KPI | 纯发送，无法统计 | `inbox.py` 轮询数据库 |
| 线索表（昵称/类型/状态/来源群） | 无 | `leads.py` + CSV 导出 |
| 首月 6 项关键指标 | 无 | `report.py` 周报 |
| 不得出现违规开票暗示 | 无 | `guard.py` 发送前校验 |
| 每周砍掉没反馈的群 | 无 | 周报里的砍群建议 |

## 二、模块划分（单向依赖）

```
campaign.py   内容编排：引导语/正文/钩子
scheduler.py  时间：绝对时间事件表 + 每周上限
planner.py    计划：把内容+目标+时间组装成可执行计划   -> 依赖 campaign, scheduler
inbox.py      接收：轮询数据库，产出「谁私聊了我」      -> 依赖 contacts
leads.py      线索：登记、状态、CSV                   -> 独立
report.py     周报：投放日志 + 线索统计 + KPI          -> 依赖 leads
guard.py      合规：违规词校验                        -> 独立
server.py     接口层：编排、调用、路由                -> 依赖以上全部
```

依赖是单向的：`server → planner → scheduler/campaign`，
`server → inbox → contacts`，`report → leads`。
没有循环依赖，各模块可单独测试。

## 三、两个关键设计取舍

### 1. 为什么用「事件队列」而不是「相对间隔」

方案要求固定时间点，而多个群依次发完要一两个小时。
串行等待会把钩子推得很晚，与「30 分钟后」不符。
改成生成按时间排序的事件表后，群 1 的钩子可以插在群 5 的主文案之前，各不相干。

### 2. 为什么接收走数据库而不是 hook

数据库里已有全部消息，`get_new_messages(user, since_seq)` 支持增量拉取，
解密读库就够。与现有架构一致，也避免注入带来的额外风控风险。

## 四、踩过的坑（都在实测中暴露）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 钩子比计划早 29 秒落库 | `import datetime` 拿到的是模块，`datetime.fromisoformat()`/`now()` 在类上，抛 AttributeError 被 `except` 吞掉，等待逻辑被跳过 | 改用 `datetime.datetime.*` |
| 2 | 合规表态被拦（「向经纪人开票即违规」） | 只看关键词，不看语境 | 加语境判断：句内含「违规/红线/预警/应当」等标志则放行 |
| 3 | 「土地承包合同」被标风险 | 风险词用了单字「包」 | 风险词全部改成具体短语 |
| 4 | 空消息池时「只发素材」发不出去 | `build_plan` 空消息池直接产出 0 条 | 有素材时按目标数补空文字占位 |
| 5 | 首次拉取灌进几百条历史 | 没有 bootstrap 概念 | 首次只记游标、不产出线索 |
| 6 | 「需要粮食财税资料」误判为高意向 | `粮食` 是领域词，人人都会提 | 高意向词改用客户/业务词，去掉领域词 |
| 7 | 从界面发素材失效 | `start()` 重建 pairs 时只保留 3 个字段，丢了 `media_path` | 展开原 pair 再覆盖 |
| 8 | 砍群建议在启用当天就把所有群判死 | 数据天然稀疏 | 要求该群两周都真有投放才给结论 |
| 9 | `/api/campaign` 返回 404 | 误加进 `do_POST` | 挪到 `do_GET` |

**教训**：单元测试只能证明「时间算得对」，证明不了「执行器读得对」。
第 1 条就是端到端才暴露的 —— 单元测试全绿、实际早发 29 秒。

## 五、数据文件与隐私

| 文件 | 内容 | 是否提交 |
|---|---|---|
| `data/campaign.txt` | 引导语/正文/钩子（正文含真实联系方式） | **不提交** |
| `data/campaign.example.txt` | 模板（联系方式是占位符） | 提交 |
| `data/leads.json` / `leads.csv` | 真实昵称与会话内容 | **不提交** |
| `data/inbox_state.json` | 私聊会话游标 | **不提交** |
| `data/schedule_state.json` | 每周投放计数（含群名） | **不提交** |
| `data/delivery_log.jsonl` | 逐条投放记录 | **不提交** |
| `data/settings.json` | 调度配置 | **不提交** |

## 六、已知局限

1. **「组长深度沟通」无法自动测量** —— 真实沟通发生在微信里，
   报表用线索状态（已转组长/已成交）近似，需人工核对。
2. **砍群建议依赖线索的「来源群」字段** —— 未登记时无法把私聊归因到群。
3. **多账号** —— 只能操作当前登录的微信账号。
4. **合规词表是有限的** —— 只能拦住已知措辞，不能替代人工判断。
