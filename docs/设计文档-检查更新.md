# 设计文档：检查更新

- 版本：v1.9.0 起
- 目标：让用户知道「有没有新版本」，并能直接拿到新安装包

## 一、为什么不做静默自动更新

这是本功能最重要的一个取舍，先说清楚。

electron-updater（Electron 官方的自动更新方案）能实现「后台下载 + 重启后自动替换」，
但这个项目**不适合**用它，理由三条：

1. **没有代码签名**。Windows 上未签名程序的静默更新失败面很大：
   SmartScreen 拦截、企业安全软件拦下载、NSIS 助手式安装器忽略静默参数等。
   一旦某台机器上升级链断掉，用户看到的是「点了更新没反应」——
   这比没有这功能更糟，因为他不知道该怎么办。

2. **项目没有 `publish` 配置**。electron-updater 依赖打包时生成的 `app-update.yml`，
   要改 `package.json` 的 `build.publish`，会让以后的发布流程跟 GitHub 强耦合
   （本地打包 + 手动 `gh release` 这套流程就跑不通了）。

3. **要多一个依赖**。本项目的原则是不轻易加依赖；而「查一下有没有新版」
   用标准库 urllib 就够，没必要为此背一个更新器。

所以本功能做的是：**检查 → 展示更新说明 → 下载到本地 → 用户自己点安装**。
一步之差的体验，换来的是「不会静默坏掉」。

## 二、版本号从哪来（关键前提）

`package.json` 里的 `version` 恒为 `1.0.0` —— 因为 `build.js` 只在构建期间临时改成
目标版本，构建完就还原。这是当初为了「命令行指定版本号」做的设计。

那运行时怎么知道自己是几版？

- 打包后 `app.asar` 里的 `package.json` 是**构建时那一份**（version=1.8.0 之类），
  所以 Electron 的 `app.getVersion()` 拿到的就是正确版本。
  （已实测：v1.8.0 的安装包 asar 里 version 就是 `1.8.0`。）
- `electron/main.js` 起 Python 时把 `app.getVersion()` 通过 `--version` 传过去。
- `server.py` 存进 `APP_VERSION`，检查更新时拿它跟 GitHub 上最新版比。

浏览器模式（直接 `python backend/server.py`）没有这个参数，`APP_VERSION` 为空，
检查更新会明确返回「拿不到当前版本号，无法比较」，**不会瞎猜**。

## 三、后端（backend/update.py）

### 查询

`GET https://api.github.com/repos/Alanine-gH/wechat-scheduled-sender/releases?per_page=20`

- 必须带 `User-Agent`，否则 GitHub 直接 403。
- 只取 `draft=false` 且 `prerelease=false` 的正式版。
- **按版本号取最大，不轻信接口返回顺序**（GitHub 是按创建时间倒序，
  万一有人补发一个旧版本就会错）。
- 结果缓存 5 分钟：GitHub 未认证限流是 60 次/小时，用户连点几下就可能打满。

### 版本比较

自己写，不用第三方：

```
parse_version("v1.8.10") -> (1, 8, 10, 1)     # 第 4 位 1=正式版，0=预发布
is_newer("1.8.10", "1.8.9") -> True
is_newer("1.8.0-beta", "1.8.0") -> False     # 预发布小于正式版
```

为什么不用字符串比较：`"1.8.10" < "1.8.9"` 在字典序上是成立的，但语义上 1.8.10 更新。
这种错误一旦混进更新判断，用户会被提示「有新版本」却怎么装都是旧的。

### 下载

- 写到 `<数据目录>/temp/update/`，先写 `.part` 再 `os.replace()` 原子改名 ——
  避免下到一半的文件被当成成品。
- **校验大小**：和 Release 里声明的 size 不一致就判失败。差一个字节都不行，
  因为让用户点开一个坏安装包比下载失败更糟。
- 后台线程 + 状态查询（`idle / running / done / error`），前端轮询进度。
- 同一时间只允许一个下载任务，防止连点拉出好几条 126MB 的流。

## 四、安全：下载接口不接受 URL

`POST /api/update/download` **只接受资产名（asset name）**，不接受 URL：

```json
{"asset": "WeChatSender-1.9.0-x64.exe"}
```

服务端拿到名字后**自己重新去 Release 里查**这个资产，取它的
`browser_download_url` 再下载。而且传了名字也必须在这次 Release 的资产列表里存在。

为什么这么较真：如果接口接受 URL，它就是一个现成的 SSRF 跳板 ——
本服务只在 127.0.0.1 上监听、又带 token，但渲染进程/本地其它程序都可能调到它。
多花二十行代码，换掉一个可被利用的接口，值得。

同理，`wcs:open-path`（打开下载好的安装包）在主进程里做了**路径白名单**：
只允许打开 `<安装目录>/temp/update/` 目录下的文件。
不加这层，等于给渲染进程一个「执行任意本地文件」的入口。

## 五、前端

位置：「6 · 设置与运维」卡片底部。

- 显示「当前版本」，来自 `GET /api/app`
- 「检查更新」按钮 → `GET /api/update/check?refresh=1`（手动点绕过 5 分钟缓存）
- 启动后 5 秒**静默查一次**：只有发现新版本才展开面板；
  没更新、或查询失败（断网/限流）都不占地方、不弹窗打扰
- 有更新时：显示版本跳转、发布日期、更新说明（已去掉 Markdown 记号）、
  「下载安装包（126.6 MB）」+「打开发布页」
- 下载中显示 `已下载 / 总数（百分比）`，完成后按钮变成「打开安装包」

## 六、验证记录

静态检查（`temp/_chk_update.py`，8 组共 30 项）全通过，含：版本比较 10 个用例、
路由归属（读接口在 do_GET）、JS 语法、IPC 对齐、id/函数齐全。

真机实测（真打 GitHub API）：

| 场景 | 结果 |
|---|---|
| 当前 1.7.0 | latest=1.8.0，has_update=true，资产 `WeChatSender-1.8.0-x64.exe` 132,753,220 字节 |
| 当前 1.8.0 | latest=1.8.0，has_update=false |
| 下载（用 136KB 的 blockmap 快测） | state running→done，落盘 136,939 字节，**MD5 与本地构建产物一致** |
| 界面（有更新） | 「发现新版本 v1.8.0」+ 说明 + 下载按钮，说明已转纯文本 |
| 界面（无更新） | 「已是最新版本」，操作区隐藏 |

## 七、已知局限

1. **未认证限流 60 次/小时**。正常使用（一天点几次）远够用；
   如果做「每小时自动查」，要改成带 token 或走别的接口。
2. **下载 126MB 需要时间**，且不校验代码签名（本来就没签）。
   所以下载完只做大小校验，是不是「正版」依靠 HTTPS + GitHub 来源可信。
3. **不做增量更新**（`.blockmap` 是 electron-builder 顺手产出的，本功能没用它）。
   每次都是整包下载。
