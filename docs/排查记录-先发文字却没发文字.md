# 排查记录：「设置了先发文字，结果只发了素材」

- **发现时间**：2026-11-05
- **现象**：用户在「素材与文字顺序」选了「先发文字，再发素材」，点开始发送后
  群里只有素材、没有文字。怀疑没保存，保存后重试仍然一样。
- **严重程度**：中高 —— 内容发不出去，但界面不报任何错
- **修复版本**：v1.9.2

## 一、先说结论

两个独立问题叠在一起：

| # | 问题 | 后果 |
|---|---|---|
| 1 | **开始发送复用了旧计划** | 计划是「消息池还空着」时生成的，`text` 是空字符串；之后补了文字却没重建计划，于是每次都只发素材 |
| 2 | 编排模式下 `media_first` 被**硬编码为 True** | 界面上「先发文字」这项设置在内容编排／自动运行路径里被静默忽略 |

## 二、问题 1：旧计划复用（直接原因）

前端 `start()` 原来直接把之前预览生成的 `state.plan` 发回后端：

```js
body: JSON.stringify({plan: state.plan, ...})
```

后端 `/api/start` 也照单全收：

```python
plan = body.get("plan") or RT.plan
```

而 `planner.build_plan()` 在**消息池为空但配了素材**时会故意补空文字占位：

```python
if not messages:
    if media_by_target and per_round > 0:
        picked = [""] * per_round      # 「只发素材」模式
```

所以只要预览是在消息池为空时点的，计划里每条 pair 的 `text` 就是 `""`。
用户随后把文字补进消息池并保存，但**没有重新生成计划**，
每次「开始发送」用的还是那份旧计划 → 只发素材，重试也一样。

`send_to` 里 `has_text = bool((text or "").strip())` 为假，
`_do_text()` 直接返回 True，界面上看不出任何异常，日志里也没有痕迹。

### 修法

`start()` 在真正开始前**用当前内容重建计划**（`genPlan({silent:true})`），
并处理三种中止情况（无目标 / 被规则拦下 / 计划为空），每种都把按钮恢复。

同时 `genPlan()` 失败时把 `state.plan` **置空** —— 否则重建失败后
`start()` 会拿着旧计划继续跑，等于没修。

## 三、问题 2：`media_first` 硬编码

两处：

```python
# planner.build_campaign_plan
"media_first": True,          # ← 不管界面选什么都先发素材

# server._run_events（编排/自动运行的执行路径）
"media_first": True,          # ← 同上
```

`build_plan()`（老模式）是正确传参的，所以这个 bug 只在
**勾了「2.7 启用内容编排」或走自动运行**时出现 —— 这也解释了为什么
不是所有用户都能碰到。

### 修法

- `build_campaign_plan()` 增加 `media_first` 参数并透传到事件
- `server.py` 的 `/api/plan` 编排分支把 `media_spec["media_first"]` 传下去
- `_run_events` 用 `bool(ev.get("media_first", True))` 而不是硬编码

## 四、顺手加的可诊断性

`_send_one` 里加一条警告日志：某条有素材但没有文字时，

```
WARN  测试群A：本条没有文字，只发素材（若你本意是发文字，请重新生成计划预览）
```

以前这种情况**完全静默**，用户只能看到「发出去了」，不知道该怀疑哪里。
现在运行日志会直接点出原因。

## 五、验证

### 1) 编排层（假引擎，不需要微信，12/12 通过）

把 `open_chat / send_text / send_media / clear_input` 等底层动作换成记录器，
直接跑 `SendEngine.send_to`，验证调用顺序：

| 场景 | 实际调用顺序 |
|---|---|
| 先文字后素材 | `clear_input → send_text → send_media` ✔ |
| 先素材后文字 | `clear_input → send_media → send_text` ✔ |
| text 为空 | 不调用 send_text，只发素材 ✔ |
| 素材失败 | 必须 ok=False（先文字模式下也报错）✔ |
| 文字失败 | 必须 ok=False ✔ |

结论：编排层本身是对的，问题一定在上游传参 —— 这条测试把排查范围直接砍掉一半。

### 2) planner 传播（7/7 通过）

- 编排模式：`media_first=False/True` 时事件里带的都是对应值 ✔
- 老模式：pair 里文字与素材同时存在，顺序正确 ✔
- 复现：消息池为空 → pair 的 text 确实是空串（确认这就是成因）✔

### 3) 真实 HTTP + 界面注入（最接近用户现场）

在浏览器里把一份「text 为空、带素材」的旧计划塞进前端状态，再点「开始发送」：

| 检查项 | 结果 |
|---|---|
| 点击前 `state.plan` 的 text | `""`（复刻用户现场） |
| 点击后 text | **31 字**（取自当前消息池）→ 证明重建生效 ✔ |
| 计划里的 `media_first` | 随界面选择变化（false / true）✔ |

## 六、教训

1. **「预览」和「执行」不能共用同一份可变状态而不校验新鲜度**。
   要么执行前重建，要么把计划与内容版本号绑定。这是最容易造成
   「我明明改了却没生效」的设计。
2. **静默降级要有痕迹**。消息池为空时补空文字本身是合理设计（支持只发素材），
   但它必须让用户看得出来 —— 现在有日志了。
3. **硬编码的默认值最危险的地方在于它不会报错**。
   `media_first: True` 写得像「合理的默认」，实际是把用户设置整条吞掉。
