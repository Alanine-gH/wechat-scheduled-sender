# 设计文档：设置中心与自动运行（v1.3.0）

- **日期**：2026-11-03
- **目标**：把「能不能长期无人值守跑下去」这件事做扎实

## 一、这轮为什么加这些设置

先说判断依据，而不是功能清单 —— 这套工具是「每天定点发」的长期常驻程序，
所以设置的价值排序看的是**它是否影响长期可用**：

| 优先级 | 设置 | 不加会怎样 |
|---|---|---|
| P0 | 自动运行（到点自己跑） | 方案要求每天晚 8 点发，人不可能天天手动点，第三天就断了 |
| P0 | 发送时段限制 | 半夜发消息最容易招投诉，比不发更糟 |
| P0 | 每日上限 / 单次上限 / 连续失败中止 | 手滑点两遍、或微信群打不开时一路失败到底 |
| P1 | 账号冷却（连发 N 条休息） | 一口气连发几十条最像机器人 |
| P1 | 重试 / 回读超时 / 清空开关 | 偶发失败被当成真失败 |
| P1 | 私聊自动轮询 + 可配关键词 | 得手动点；业务词写死在代码里，不可调 |
| P2 | 日志与截图保留天数 | 30 群 × 每天 2 张 × 365 天 ≈ 2 万张，磁盘迟早满 |

## 二、模块结构

```
settings.py     配置中心：27+1 个键的默认值与表单描述、校验、读写
   ↑（只被读取，不反向依赖）
autorun.py      自动运行判断：该不该跑 + 跑过没有     <- 不依赖 server
housekeeping.py 自动清理：只删自己产生的东西
inbox.py        接收：轮询私聊，关键词可传入
   ↓
server.py       编排：把上述能力接到 HTTP 与执行器
```

`autorun.py` 刻意不依赖 `server.py`：它通过 `run_fn` 注入「怎么跑」，
自己只回答「现在该不该跑」。所以它能脱离整个服务单独测试（实测 8 个分支）。

## 三、几个值得说明的设计决定

### 1. 配置用「默认值 + 覆盖」而不是直接读文件

`load()` 以 `DEFAULTS` 为底、文件值覆盖。好处是**新增设置项时老配置文件不会缺键**，
取值处也不必到处写 `or 默认值` —— 后者正是配置失控的起点。

### 2. 保存时只接受声明过的键

拼错的键写进 JSON 不会报错，但永远不生效 —— 这是最难查的一类问题。
`save()` 直接拒掉未声明的键。

### 3. 按天去重存「日期」而不是时间戳

自动运行判断的是「今天跑过没有」，存 `2026-11-03` 最直观，
也避开了时区与夏令时的边界问题。

### 4. 先记「今天已跑」再真正执行

万一跑到一半程序被关掉，重启后不该在同一天再补一轮 ——
**重复发送比漏发严重**。

### 5. 补跑宽限（默认 30 分钟）

晚上 23 点才打开程序时立刻发一轮，比不发更糟。超过宽限就跳过当天。

### 6. 清理只删自己产生的东西，并且要能说清删了什么

严格限定在 `shots/` 下的日期目录（名字必须匹配 `^\d{8}$`）与
`delivery_log.jsonl`。删除结果返回清单并写运行日志 ——
默默删掉的话，用户某天发现截图没了会以为是 bug。

## 四、踩过的坑

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 状态里 `grace_minutes` 是 None | `schedule_config()` 漏透出 `auto_grace_minutes`，`due()` 读不到回落到 0（=过点绝不补跑），程序晚开一分钟就永远不发 | 补上该字段 |
| 2 | `interval_min: 0.05` 被拒 | 契约就是这么写的（min 0.1） | 这是校验生效，不是 bug |

第 1 条值得记一笔：**测试时因为 `start_at` 恰好等于当前时间、`late_min≈0`
而侥幸通过**，是查看状态时发现字段为 None 才揪出来的。
和上一轮那个 `datetime` 的 bug 同一类 —— 测试的输入恰好落在边界上时，
缺陷会隐身。

## 六、已知局限

1. **自动运行依赖程序常驻**。关掉程序就不会自动发 —— 这是设计选择
   （不注册系统服务，避免装出一个用户看不见的后台进程）。
2. **`auto_grace_minutes` 之外没有「补跑」机制**。若整天没开程序就跳过那天，
   不会在次日连发两天份。
3. **清理不碰用户主动保留的文件**。想长期留存的截图请自行移出 `shots/`。
4. **关键词仍可能误判**。可配置只是让它可调，不等于准确。
