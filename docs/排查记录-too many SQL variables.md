# 排查记录：联系人面板「读取失败：too many SQL variables」

- **发现时间**：2026-11-04
- **触发环境**：用户机器（账号 `wxid_z0jmpj2dnwyq12`），群与成员数量远超开发机
- **严重程度**：高 —— 联系人面板打不开，等于整个工具不可用
- **修复版本**：v1.9.1

## 一、现象

用户机器上打开程序，「1 · 账号与目标」的联系人下拉框显示：

```
读取失败：too many SQL variables
```

开发机（29 个群 / 7 个好友）从未复现。

## 二、定位

1. `contacts.py` 自己没有 IN 子句，好友查询是无参数的全表过滤。
2. 报错发生在 `db.get_groups()`（第三方库 `wechatauto` 的实现）。
3. 看它的源码，问题一目了然：

```python
placeholders = ",".join("?" * len(room_by_id))       # 占位符数 = 群数
... WHERE room_id IN (%s)
member_ids = ...                                      # 全部群的成员去重集合
mp = ",".join("?" * len(member_ids))                  # 占位符数 = 成员总数！
... WHERE id IN (%s)                                  # ← 这里炸
```

第二个 IN 的占位符数量 = **所有群的成员总数**。

4. 为什么开发机没事：SQLite 的参数上限，老版本是 **999**，3.32+ 提到 **32766**。
   开发机 29 个群 ≈ 1.3 万成员 id，在 32766 以内；
   用户机器群多、成员多，超过了 32766。

也就是说这是一个**只在大账号上爆**的问题 —— 越是用户多的微信号越炸。

## 三、为什么不直接改那个库

`wechatauto` 是 pip 依赖（wechatauto-replica），改它的 site-packages：

- 用户机器上是另一份，改了这份改不了那份；
- 升级/重装即被覆盖；
- 属于第三方代码，改动不可追溯。

正确做法：**在自己的 `contacts.py` 里重写群枚举**。
本来好友查询就已经在用它的 `_contact_conn()` 拿连接了，这条路是现成的。

## 四、修法（backend/contacts.py）

新增 `_enumerate_groups(conn, with_members)`，三张表自己查：

| 数据 | 查法 | 是否用 IN |
|---|---|---|
| 群列表 | `SELECT id, username, owner FROM chat_room` | 否 |
| 群名 | `… FROM contact WHERE username LIKE '%@chatroom'` | 否 |
| **成员计数** | `SELECT room_id, COUNT(*) … GROUP BY room_id` | **否**（一次拿全部群的计数） |
| 成员详情 | 先拉全量 `room_id/member_id` 映射，再对去重后的成员 id **按 900 一批**分片查 contact | 是，但分批 |

关键点：成员**计数**完全不需要 IN（GROUP BY 就行），所以主界面那条路径
（只要计数、不要成员名单）**一个占位符都没有**；
成员详情只在 `with_members=True` 时才查，且分片大小 900 ——
老版本 SQLite（上限 999）和新版本（32766）都安全。

附带收益：主界面枚举群不再需要拉全部成员详情，**比原来快**。

## 五、验证

### 1) 复现 + 回归（temp/_t_groups.py，13/13 通过）

构造极端库：60 群 × 800 成员 = **48000 条成员记录、40000 个去重成员 id**（> 32766）。

- **A 复现**：旧写法一次性 IN 40000 个 id → 确实报
  `too many SQL variables` ✔（证明根因找对了）
- **B 新实现**：60 群、每群成员计数 800、群名/群主/成员详情/is_owner 全部正确 ✔
- **C 分片边界**：0 / 900 / 901 / 40000 个 id 都正常 ✔

### 2) 等价性测试（temp/_t_equiv.py）

在新旧实现之间逐字段比对（群数量 / username 集合 / 群名 / 群主 / 成员数 /
成员集合 / is_owner）。本次开发机上微信未登录，**尚未跑成**；
下次在登录了微信的机器上执行即可。SQL 列名直接取自库自身的查询，
构造上不会错，但这条验证仍然值得补。

## 六、教训

1. **「在我机器上是好的」在这种问题上没有意义** —— 参数上限类错误只在数据量
   超过阈值时爆，而阈值取决于用户机器的 SQLite 版本和数据规模。
   写带占位符的 SQL 时，数量来自用户数据就必须分批。
2. **成员计数不需要 IN**。`GROUP BY` 一次拿全部计数，比「先拼 1 万个占位符」
   又快又安全。这条以后写任何聚合查询都适用。
3. 第三方库的接口不等于可依赖的实现。涉及大数据量的调用，宁可自己写。
