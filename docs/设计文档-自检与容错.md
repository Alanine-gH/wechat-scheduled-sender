# 设计文档：自检、失败补发、备份与群管理（v1.4.0）

- **日期**：2026-11-03
- **目标**：不再加「功能」，而是补**长期使用的四条命脉**：
  出问题能诊断、失败能补、数据不会丢、没反馈的群能真的降下来

## 一、这一轮解决的四个问题

| # | 问题 | 不做会怎样 |
|---|---|---|
| 1 | 出问题时只能靠人远程猜 | 微信一升级控件树就失效，定位一次要很久 |
| 2 | 失败只记在内存里 | 程序一关就不知道哪些没发出去，无从补发 |
| 3 | 积累的数据没有退路 | 线索表/文案/配置误删一次就白干 |
| 4 | 砍群只有建议没有动作 | 用户记不住哪个群该少发，建议等于没提 |

## 二、四个模块

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `doctor.py` | 11 项健康自检 | **每项独立容错**；每项给 hint |
| `failures.py` | 失败登记与补发 | **按内容记账**，成功自动销账 |
| `backup.py` | 备份与恢复 | **导入前自动快照**；**防路径穿越** |
| `targets.py` | 目标投放状态 | 降频=隔天，暂停=不发；恢复正常删记录 |

依赖仍是单向的：`server -> 各模块`，各模块互不依赖，都能单独测试。

## 三、几个设计决定

### 1. 自检必须每项独立容错

最需要自检的场景恰恰是「环境已经坏了」。如果一项抛异常就把整个诊断打断，
那它在该用的时候用不了。所以每项都包在 try/except 里，异常本身变成一个
error 结果 + 修法提示。

### 2. 失败按「内容」记账，不按流水

用 `target|kind|text|media` 算一把钥匙。好处：
- 同一目标同一条内容反复失败，只累加次数，不会堆出几十条待办
- 重发成功后，按同一把钥匙自动销账，**不需要人工核对哪条补过了**

补发因此就是「拿待办当计划跑一遍」，复用同一套事件执行器 ——
不另写第二条发送路径（两条路径迟早跑偏）。

### 3. 备份的两条硬约束

- **导入前自动快照**：直接覆盖用户积累是最不可原谅的操作，恢复错了必须能退回
- **绝不 extractall**：zip 里的名字一律取 basename + 白名单校验，
  恶意的 `../../` 能往系统目录写文件

### 4. 降频用「隔天」而不是「每周几天」

方案要的是「降低频率」。隔天是最小改动且一眼能懂；按周几发会与
`run_days` / `hook_days` 叠加，条件一多就容易算错。

## 四、踩过的坑（这轮三个，其中两个是重复犯错）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 自检报「控件树无法实体化」，但单独跑脚本是好的 | UIA 依赖 COM，COM 是**按线程**初始化的；HTTP 处理线程没 CoInitialize | 检查前显式 `init_com()` |
| 2 | **自动清理从来没生效过** | `schedule_config()` 漏透出 `shot_keep_days`/`log_keep_days`，回落到 0（=不清理） | 补进投影；并注释警告 |
| 3 | `GET /api/failures` 返回 404 | 读接口被写进 `do_POST` | 移到 `do_GET`；写了路由检查脚本兜底 |

第 1、2 条都是自检自己抓出来的 —— 这个工具第一次跑就发现了两个静默失效的功能。

第 2 条和上一轮的 `auto_grace_minutes` 是**同一个模式**：
**投影函数漏字段 -> 取值回落默认 -> 功能静默失效**，而且不报错。
根因是 `schedule_config()` 这种手工维护的投影列表本身就是错因 ——
新增设置时忘了加，功能就悄悄没了。现在已在函数里加了醒目注释。

第 3 条也是重复犯错（上一轮 `/api/campaign` 同样问题）。这次补了个
`temp/_routes.py` 检查脚本，把 do_GET/do_POST 注册的路由全列出来，
核对「应是 GET 的读接口」是否都在 do_GET 里。以后每次改路由都该跑一下。

## 六、已知局限

1. **自检覆盖的是「已知」故障点**。微信换了全新的失效方式，自检仍然会说正常。
2. **补发不区分「当时失败」和「后来已经被别的途径发过」** ——
   若用户手工补过，再点补发会重复发一次。
3. **备份不含截图与密钥**（有意为之：体积大且敏感）。
4. **降频是固定隔天，不支持自定义频率**。
