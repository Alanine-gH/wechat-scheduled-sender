# 设计文档：v2.0.0 三处改动

v2.0.0 是发布版号上的一次跨越，包含三件互相独立的事：
截图存档开关、百度网盘分发入口、微信数据目录定位增强。

---

## 一、截图存档开关

### 需求

截图是「发送证据」的一部分（配合回读校验）。但不是每个人都需要，而且
`shots/` 会持续增长、也留下聊天画面。加一个开关让用户自己决定。

### 实现

| 位置 | 改动 |
|---|---|
| `settings.py` | 新增 `shot_enabled`（bool，默认 **True**），归入「可靠性」组 |
| `server._send_one` | 关闭时 `shot_path = None` |
| `sender.send_to` | 本来就有 `if shot_path:` 判断，**无需改动** |
| 主界面「6 · 设置与运维」 | 复选框 + 状态文字，改动即写入设置（单项 patch） |
| 设置页 | 由 schema 自动渲染，无需单独写代码 |

关键点：**开关只影响截图，不影响发送与回读校验**。后者才是「真发出去了」的证据，
不能因为省磁盘而丢。界面上的说明文字也是这么写的。

顺带把运行日志下方那句「截图保存在 shots/&lt;日期&gt;/」做成动态的 ——
关掉后继续显示这句会误导用户去空目录里找。

保存失败会把复选框回滚，不让界面显示一个没落库的状态。

## 二、百度网盘分发入口

### 背景

用户主要在国内，GitHub 访问不稳定。新版会同时传到百度网盘。

### 实现

- 链接与提取码放进**设置**（`pan_url` / `pan_code`，归入新的「关于」组），
  而不是硬编码在代码里 —— 换分享链接不用重新打包。
- `GET /api/app` 一并返回这两个字段。
- 主界面「6 · 设置与运维」新增「百度网盘下载」按钮 + 提取码提示，
  紧挨着「检查更新」，两条获取新版的途径放在一起。
- README 顶部加了下载渠道表格（GitHub 进来第一眼就能看到网盘地址）。
- 发布文案 / Release 说明里同步写上链接。

按钮用 `<a target="_blank">`：Electron 里由主进程的 `setWindowOpenHandler`
拦下并交给系统浏览器打开（不会把应用窗口导航走），浏览器模式就是新标签页。

## 三、微信数据目录定位（「部分设备读不到登录的微信」）

### 现象

部分设备上程序找不到微信账号/数据。用户看不到任何可操作的提示。

### 根因

第三方库 `wechatauto.auto_detect_db_dir()` 只探三处：微信配置文件、
注册表、`Documents`/用户主目录；目录名只认 `xwechat_files` / `WeChat Files`。

实测会踩到的机器：

| 情况 | 为什么探不到 |
|---|---|
| 微信「设置 → 文件管理」把存储位置改到别的盘 | 配置/注册表里读不到，扫描范围也没覆盖 |
| 绿色版 / 多开版 | 注册表无记录 |
| 目录名是中文「微信文件」 | 名字不在白名单 |
| 企业环境把「文档」重定向到网络盘 | 用户目录指向不对 |

这些机器上数据其实都在，只是**没找到**。

### 实现：backend/wxdir.py

三层策略，可靠性从高到低：

1. **用户手动指定**（设置 `wechat_db_dir`）—— 一定最准；
2. 第三方库的自动探测（保持向后兼容）；
3. **自己再扫一遍**：所有盘符根目录、`Documents`、`AppData`、`Tencent`
   下的一层常见目录名。

每一层都要求「目录下确实存在含 `db_storage` 的账号目录」才算命中，
避免把空壳目录当微信数据目录（有些机器的 `xwechat_files` 是空的）。

**用户填到哪一级都能用**（`_probe` 负责对齐）：

```
E:\微信文件                      ← 父目录
E:\微信文件\wxid_xxx_abcd        ← 账号目录
E:\微信文件\wxid_xxx\db_storage  ← db_storage
带引号（从资源管理器复制）         ← 去掉引号
```

让用户自己判断该填到哪一级是不现实的，所以三种都接受，末尾反斜杠、
引号也一并处理。

### 接入方式

`contacts.py` 新增 `_resolve_db_dir()`，`get_db()` 与 `list_local_accounts()`
都先定位再传给库（`list_accounts(db_dir=...)` 本来就支持这个参数）。
找不到时抛的错也变成可操作的话：

> 未找到微信数据目录。请在「设置 → 微信连接」里手动指定微信文件目录
> （微信里：设置 → 文件管理 可以看到实际路径）

### 诊断

- `GET /api/wxdir`：返回定位到的目录、来源（手动/自动/扫描）、账号列表与最近活动
- 设置页「微信连接」组下面有「检测微信数据目录」按钮，直接看到结果与账号表
- 健康自检新增第 12 项「微信数据目录」：找不到时给 error + 具体操作指引

### 顺带：把「当前登录账号靠猜」这件事说清楚

`is_current` 一直是用「db 文件最近修改时间最大」推断的 —— 不可靠。
现在多个账号活跃时间相差小于 10 分钟时，会给每个账号打上
`current_uncertain: true`，前端可据此提示用户自己确认。
（这一版只做标记，不改判断逻辑：真要准确判断得从微信进程/UIA 拿，
那是另一个工作量。）

| 项 | 结果 |
|---|---|

| 接口测试（真实服务） | 17/17：版本/网盘字段、wxdir 诊断、截图开关关→开、设置项 34 项、无效路径不崩 |
| 界面验证 | 设置页「关于 + 微信连接 + 检测」、主界面网盘按钮与截图开关，均截图确认 |
| 健康自检 | 12 项，0 异常（微信版本 4.2.0.13 未列入验证名单属已知提醒） |
| **真实大账号等价性** | 173 群 / 13307 成员：新旧群枚举实现逐字段完全一致（群名、群主、成员数、成员集合），好友 398 个 |
| 静态检查 | Python 语法 7 个文件、前端两页 JS、id/函数/路由/设置项一致性，全通过 |

最后一项同时印证了 v1.9.1 的修复：这个账号 13307 个成员 id 仍在 SQLite 上限
（32766）内，所以旧实现还能跑；用户那台超过上限就报了
`too many SQL variables`。

## 五、已知局限

1. **全盘扫描只在常见位置找**，不会真的遍历整个磁盘（太慢）。
   极端自定义路径仍需手动指定。
2. **`is_current` 仍是推断**，只是现在会把不确定性暴露出来。
3. 百度网盘是**人工同步**的：发新版要记得两处都更新，软件不会替你上传。
