# 排查记录：群成员筛选浮层误判 + 运行日志空白

- **日期**：2026-11-11
- **版本**：v2.0.4（与上一轮「控件树空壳 / 引擎错误展示」合并发布）
- **涉及文件**：`backend/myhistory.py`、`backend/server.py`、`frontend/index.html`

## 用户报告的两个现象

1. 结果表格里显示「点了「群成员」但筛选面板没打开（试过 selection / legacy /
   click / focus+space）。已停止，避免把昵称搜成全群消息」，而**用户提供的微信
   截图里，筛选面板其实已经打开**——右侧有「搜索群成员」输入框和 K / R 分组的
   成员列表（Krystal_Star、软工2404周传根、软工2404郑天成、软工2404陈强）。
2. 「为什么查找不在日志里面显示」——下方「运行日志」面板一直停在「等待开始…」。

## 现象 1：结构性误判，不是点击失败

### 证据（`logs/myhistory_tree_20261111_165439.json`，16:54:50 本次失败转储）

`stage[1]` 有 4 个窗口，其中新增的 `hwnd=3543640` 是**独立顶层浮层**：

| 字段 | 值 |
|---|---|
| 根窗口 | `WindowControl name='Weixin' cls=mmui::XPopover` |
| 搜索框 | `EditControl name='搜索' cls=mmui::XValidatorTextEdit` |
| 成员列表 | `ListControl aid=chatroom_member_ cls=mmui::StickyHeaderRecyclerListView` |
| 列表项 | 4 个带名字的 `ListItemControl` |
| 包围盒 | 328×392（能通过 `_roots` 的 200×150 过滤） |

### 根因

`_is_member_search()` 只在 `Name / AutomationId / ClassName` 里找
`MEMBER_SEARCH_NAMES`（「搜索群成员」「搜索成员」…）。**微信 4.2.0.13 把浮层里
成员搜索框的 Name 退化成裸「搜索」**，与聊天记录窗口顶部的全局搜索框完全同名：

- `_is_member_search()` → 恒 False → `member_open=False`
- `_is_global_search()` 恰好把 `Name=='搜索'` 判成全局框
- `member_panel_ready()` 返回 False → `wait_member_panel()` 超时 → 主动刹车

这是 v2.0.2 那套防误截逻辑在**正确地**刹车，只是输入信号错了。文案本身也误导：
它建议「用探测控件树导出真实控件名填到设置」，但这次根本不是控件名问题。

### 修复：结构双重证据，不依赖文案

| 处 | 改动 |
|---|---|
| 新常量 | `MEMBER_PANEL_CLASSES=("mmui::XPopover",)`、`MEMBER_LIST_MARKS=("chatroom_member", "stickylistrecycler", "stickyheaderrecyclerlistview")` |
| 新函数 `_panel_signature(root)` | 遍历窗口树，收集「浮层类名 / 成员列表 / 有名列表项数 / 所有 EditControl」，`is_panel = popover and (member_list or items>=3)` |
| `search_state()` | **按窗口分组**：浮层窗口里的 EditControl 才是成员框；其它窗口里 `Name='搜索'` 一律按全局框处理，即使文案像成员框也不认。`member_open` 额外要求 `panel_open` |
| `_page_down()` | 优先聚焦浮层的判定从旧 `_is_member_search` 换成 `_panel_signature(...).is_panel`——否则 4.2.0.13 上会滚错窗口 |
| `_clear_global_search()` | 跳过浮层窗口，避免把成员搜索框当全局框清掉 |
| 失败文案 | 改成「没确认到筛选浮层」+ 三步可操作指引 + `search_state` 诊断值（浮层/成员框/全局框有值），删掉「填到设置」的误导 |

### 为什么不会重演「47 张全群消息」

新判定**更严**：必须同时满足「浮层类名 + 成员列表证据 + 至少一个 EditControl」才认成员框。
回归测试覆盖了三个反例：无浮层时 `member_open=False`、全局框被写脏时
`member_panel_ready=False`、`find_member_search()` 返回 None。

## 现象 2：运行日志空白是设计漏接

「运行日志」面板 `#logs` 由 `renderLogs(s.logs)` 全量渲染，`s.logs` 来自
`server.Runtime.RT.logs`，只有群发任务写它。「我的群消息」的状态走 `myPoll()` →
只更新 `myMsg` 那一行 pill，**从没往 `RT.logs` 写过任何东西**。

修复用了可注入回调，避免 `myhistory` 反向 import `server` 造成循环依赖：

| 处 | 改动 |
|---|---|
| `myhistory._Job.log()` | 除更新 `message` 外，调 `JOB.log_sink(level, msg)`（若已注入） |
| `server.py` | `RT = Runtime()` 后加一行 `myhistory_mod.JOB.log_sink = RT.log` |
| `_worker` | 每群进度、界面结果、本地库结果、完成总结都 `JOB.log(...)` |
| `start()` | 开任务时打一条「开始查找 N 个群」 |
| `renderLogs()` | 新增行加 `.lin` 淡入动画（`@keyframes logIn`，0.28s），首屏全量渲染行为不变 |

前端不需要新增任何日志区，直接复用下方已有的「运行日志」面板。

### 排查中修正的两个测试前提错误（诚实记录）

1. E2E 首轮全失败，是因为拿 **16:40 的旧 `core.bin`** 去测 17:10 才改的源码。
   加密产物必须重新构建才包含本轮改动，不能拿旧包验新代码。
2. 一次构建用了 `node build.js ... | Select-Object -First 6`，PowerShell 提前关闭
   管道**真的杀掉了进程**（不是之前那种「exit 1 假象」），导致 `package.json`
   卡在 2.0.4、产物还是旧的。已 `git checkout -- package.json` 还原后完整重跑。

## 已知限制

1. **未做真机「界面八步截屏」端到端**：需要用户在场点「开始查找」并观察微信
   窗口被操作。已验证的是「浮层识别」这一环（用真实失败转储回归）+ 日志管道。
2. 结构证据依赖 `mmui::XPopover` 类名和 `chatroom_member_` AutomationId。
   若微信再次改版换掉这两个标识，需要用「探测控件树」导出新结构后补进常量。
   失败文案现在会把 `search_state` 诊断值直接显示出来，便于定位。
3. `log_sink` 是运行时注入的全局回调；若将来有第二个进程/第二套 Runtime，
   需重新绑定。
